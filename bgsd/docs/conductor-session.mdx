# Conductor Session

`/bgsd-sesh "<prompt>"` is the only interface you ever use. The Conductor (codename Kiwi) is always on.

You describe what you need. Kiwi detects the scale, decides how many agents to run and how deep to go, and **runs the full pipeline immediately**. Pass `--plan-only` (or `--dry-run`) to preview the plan without executing anything. The pipeline integrates everything on the standing **`next`** branch; the `next` → `main` merge is a manual, human-only step. The one hard invariant is that **agents never write to `main`** (the production branch).

You never call `/bgsd-verify`, `/bgsd-queue`, `/bgsd-run`, or any stage command directly; those are internal stages the Conductor runs for you.

## Install

bgsd is an installable, standalone Claude Code plugin:

```bash
claude plugin marketplace add filippo-fonseca/better-gsd
claude plugin install bgsd@better-gsd
```

Run `/reload-plugins` (or restart Claude Code) so the `/bgsd-*` commands bind. That is the only setup you do by hand. bgsd is **gsd-agnostic**: it does not vendor GSD. It uses the user-installed `gsd-core` plugin, and the Conductor sets up what it needs at the start of every session, so you just talk to it:

- **gsd-core.** Kiwi ensures `gsd-core` is installed and kept up to date (under the hood: `claude plugin marketplace add open-gsd/gsd-core`, `claude plugin install gsd-core --scope user`, and `claude plugin update gsd-core` to refresh). You never manage GSD by hand. After a plugin update, Claude Code needs `/reload-plugins` or a restart to apply, and Kiwi flags that when it happens.
- **Playwright.** Kiwi ensures the Playwright browser tooling (used for the computer-use / vision verification that powers Loop 1 and Loop 2) is available.

## One-time setup: `/bgsd-init`

Before the first session in a repo, run `/bgsd-init` once. It is idempotent (safe to re-run), and every `/bgsd-sesh` runs it automatically as a preflight, so you rarely call it by hand:

```bash
/bgsd-init
```

`/bgsd-init`:

- creates the standing **`next`** integration branch off the auto-detected base branch (and fast-forwards it from `main` if it already exists);
- scaffolds a persistent, committed **`.bgsd/`** master folder: `seshs/` (a queryable knowledge base of every past session), `ledger.md`, and `config.json`;
- writes a **`BGSD.md`** settings file at the repo root (the user-editable knobs, like a CLAUDE.md for bgsd);
- makes the GSD config bgsd-compatible.

## The integration branch: `next`

bgsd keeps one standing integration branch, **`next`** (the name is configurable in `BGSD.md`). It is the rehearsal mirror of production: worktree branches merge into `next`, Loop 2 verifies the integrated app on `next`, and the User Review Gate boots `next`. The `next` → `main` merge is the one step the Conductor never does for you; it is always a manual, human-only merge. At the start of every session, `next` is created if missing and fast-forwarded from `main`.

## Settings: `BGSD.md`

`BGSD.md` is the user-editable settings file (like a CLAUDE.md). Kiwi reads it at the start of every sesh, and can self-edit it when you ask it to change a setting in chat. Every knob ships with a default: the integration branch name, the model and effort posture, which `.env*` files propagate into worktrees, GitHub issue/PR behavior, and Kiwi's narration. Because git worktrees do not carry gitignored files, the Conductor copies the configured `.env*` files from the repo root into each worktree so apps boot.

## The entry point

```
/bgsd-sesh "<whatever I need>"   [--quick | --feature | --project]
```

**Examples:**

```bash
# Let the Conductor decide (auto-detect) and execute immediately
/bgsd-sesh "Fix the nav collapse on mobile below 768px"

# Quick task — no discussion, direct execution, still verified
/bgsd-sesh "Change the hero button to indigo" --quick

# Feature — no discussion, some parallelism, integration loop if >1 unit
/bgsd-sesh "Add a dark-mode toggle" --feature

# Big build — Conductor discusses with you first, then full parallel pipeline
/bgsd-sesh "Add user authentication, rate limiting, and an admin dashboard" --project

# Preview only — classify + print the plan; nothing spawns or runs
/bgsd-sesh "Add a billing dashboard" --plan-only
/bgsd-sesh "Add a billing dashboard" --dry-run    # alias for --plan-only
```

## Flags

| Flag | When to use | What changes |
|------|-------------|--------------|
| *(none)* | Default — runs immediately | Conductor reads the prompt, auto-detects scale, and executes the full pipeline. |
| `--quick` | You know it's small (a bug fix, a copy change, a minor tweak) | No pre-discussion, no brainstorm phase. Fast. Still fully verified — Loop 1 always runs. Executes immediately. |
| `--feature` | You know it's feature-sized (one coherent feature, a few units) | No pre-discussion, some parallelism, integration loop if >1 unit, formal review gate. Executes immediately. |
| `--project` | You know it's large (many features, broad scope) | Conductor **discusses with you first**: brainstorm, clarify ambiguity, confirm scope. Then full parallel pipeline. Real merges/PRs are human-gated at checkpoints. |
| `--plan-only` | You want to see the plan before committing | **Preview only.** Classify + print the depth plan; invoke zero boundaries. Nothing runs. |
| `--dry-run` | Same as `--plan-only` | Alias. Identical preview behavior. |

**A manual flag always wins, unconditionally.** The auto-scale thresholds apply only when no flag is given. `--feature` on a 2-3-unit task still runs the feature pipeline; `--project` on a tiny task still discusses with you first and runs the full pipeline. Every path — quick, feature, or project — exits through Loop 1 with a real browser check.

## Scale comparison

| | quick | feature | project |
|---|---|---|---|
| **Example** | "change this button to blue" | "add a dark-mode toggle" | "build auth + billing + a dashboard" |
| **Auto-scale trigger** | ≤2 units, 1 surface | a few units, mid-size | ≥4 units or ≥3 surfaces |
| **Upfront discussion** | no | no | yes (intake/brainstorm) |
| **Decompose + parallel worktrees** | no — single | some, low concurrency | full fan-out |
| **Integration loop (Loop 2)** | no | yes if >1 unit | yes |
| **Formal review gate** | no (Loop 1 PASS + 1-line confirm) | yes | yes |
| **Verification (Loop 1)** | always | always | always |

## Stages the Conductor runs internally

You never call these. Kiwi orchestrates all of them on your behalf as part of a `/bgsd-sesh`.

| Stage | Quick path | Feature path | Project path | Details |
|-------|:-----------:|:------------:|:------------:|---------|
| Init / preflight | always | always | always | `/bgsd-init`: ensure `next` exists + fast-forward from `main`, scaffold `.bgsd/`, write `BGSD.md`, copy `.env*` into worktrees |
| Scale classify | always | always | always | Reads prompt length, keyword heuristics, and your flag |
| Intake / discuss | — | — | always | Brainstorm, clarify scope, confirm before code runs |
| Decompose | — | some | always | Breaks prompt into a verified DAG of GSD units |
| Worktree fan-out | optional | some, low concurrency | always | Parallel isolated git worktrees, one per unit (with `.env*` copied in so apps boot) |
| **Loop 1 — verify→fix** | **always** | **always** | **always** | Real browser check after every execution; loops until PASS |
| Conflict pre-check + merge | — | if >1 unit | always | Detects conflicts; merges verified branches into the standing `next` branch in dependency order |
| **Loop 2 — integration verify→fix** | — | **if >1 unit** | **always** | End-to-end boot of the integrated app on `next`; fix agents on defects |
| User Review Gate | — | always | always | Boots `next`; per-criterion approval gate; never auto-passes |
| Feedback ingestion | on request | on request | on request | Turns review findings into another fix pass |
| CHANGELOG + PR | always | always | always | Aggregated changelog, atomic `gh pr create` into `next`; `next` → `main` stays human-only |

Throughout the run, Kiwi narrates the pipeline conversationally with the exact stage and agent names, X/Y progress counts ("4/4 agents finished, 2/4 verified and merged into `next`"), an explanation of each PR and merge, and the exact command to type at every human gate. The live status view (`/bgsd-status` machinery) runs alongside it. At any moment you can see active agents, the current stage, Loop 1 iteration counts per worktree, merge history, budget, and context pressure. ## The "same pipeline, scaled" idea

The quick, feature, and project paths are not different systems — they are the same verify-and-fix pipeline, with feature adding some parallelism and a review gate, and project adding full decomposition, parallel worktrees, Loop 2, and a formal review gate on top.

This means:

- **A one-line bug fix** still goes through the driver ladder (console → network → DOM → vision), still produces a `verification-report.json`, and still exits with a structured verdict.
- **A twelve-unit project** goes through exactly the same loop per worktree, then a second loop over the integrated build, then your explicit sign-off.

The only thing that changes is scale. The guarantees are constant: no silent green, bounded iterations, and agents never writing to `main` (everything integrates on `next`, and `next` → `main` stays human-only).

## Driver ladder (all paths)

bgsd's four-rung verification ladder runs in every Loop 1 and Loop 2 cycle:

| Rung | Tool | Catches |
|------|------|---------|
| 1 · Console | `browser_console_messages` | React warnings, hydration errors, JS exceptions |
| 2 · Network | `browser_network_requests` | 4xx/5xx, failed resource loads |
| 3 · DOM | `browser_snapshot` | Wrong structure, missing elements, unmet criteria |
| 4 · Vision | `browser_take_screenshot` | Purely visual criteria (last resort only) |

**No silent green.** `BLOCKED` if the Playwright MCP is absent. `INSUFFICIENT_EVIDENCE` if evidence is thin. A `FAIL` is always called a `FAIL`.

## Conductor personality

Kiwi speaks in a refined British-butler voice: courteous, calm, conspicuously competent. It narrates progress, checkpoints, and merge decisions in plain English. Structured outputs — verdict lines, `verification-report.json`, YAML frontmatter, error signals — stay strictly literal and machine-parseable. The butler never softens a `FAIL` into something that sounds like a pass.

See [`PERSONALITY.md`](../PERSONALITY.md) for the full voice contract.
