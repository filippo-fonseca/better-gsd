# bgsd Documentation

bgsd is an open-source, installable Claude Code plugin that layers autonomous, self-verifying orchestration on top of GSD. Lightweight to install (markdown files and a handful of zero-dependency Node scripts), but ultra-potent in what it does. The single entry point is the **Conductor Session** (`/bgsd-sesh`). All other pages document the internal stages the Conductor orchestrates on your behalf.

## Install

```bash
claude plugin marketplace add filippo-fonseca/better-gsd
claude plugin install bgsd@better-gsd
```

Then run `/reload-plugins` (or restart Claude Code) so the `/bgsd-*` commands bind. bgsd is **gsd-agnostic**: it does not vendor GSD. It uses the user-installed `gsd-core` plugin, and the Conductor (default name **Kiwi**, customizable in `BGSD.md`) keeps that dependency current and ensures the Playwright browser tooling is available, all at the start of every `/bgsd-sesh`. You just talk to the Conductor; it sets up what it needs. See the [Quickstart](./quickstart.mdx) for the full walkthrough.

A repo is set up once with the idempotent `/bgsd-init` command (also run automatically as a `/bgsd-sesh` preflight): it creates the standing **`next`** integration branch off the auto-detected base branch, scaffolds the persistent `.bgsd/` master folder (`seshs/`, `ledger.md`, `config.json`), and writes a user-editable `BGSD.md` settings file. The pipeline integrates everything on `next`; agents never write to `main`, and the `next` → `main` merge is always manual and human-only.

All pages are valid standalone Mintlify MDX. They are intentionally kept outside GSD's vendored nav config (`mint.json` / `docs.json`) — editing that file would violate the "never edit vendored GSD" rule. To surface bgsd in the docs site nav, add a single group entry to the Mintlify nav config pointing at these pages (see the note at the bottom of any page).

## New in this release

Recent additions to how the Conductor runs and talks to you (bgsd 0.8.2). For the exact flag on any command, see the [Commands Reference](./commands-reference.mdx).

### How bgsd picks models

bgsd assigns a model and effort to each pipeline role. The guiding principle: spend the priciest model (**Claude Fable 5**, very token-hungry) **only where reasoning-leverage is high and token-volume is low**, and keep building and raw-file reading cheap. So the scout never reads raw files on Fable (a Sonnet scout does that) and review is never Fable (a fresh-context Opus does it). Two structural limits shape everything below. First, bgsd **cannot force the Conductor's model**: the Conductor is your own live session, so bgsd only *nudges* it via `/model` (both ways) and honors whatever you're on. Second, the in-session agent tool is **opus/sonnet/haiku only** — bgsd **cannot spawn a Fable subagent in-session**. Fable therefore runs in exactly two places: (1) as the Conductor's own session, if you happen to be on Fable, or (2) as a whole **per-unit worktree subprocess** launched via `claude -p --model claude-fable-5` for hard units (difficulty ≥ 0.5). There is no `settings.json` model seed and no per-agent Fable approval gate.

Everything below is a **default**. The Conductor decides per unit and adapts as a run unfolds, and you always have the final say: override per-unit or per-session, by flag, in `BGSD.md`, or by just telling the Conductor, and it re-plans on the fly.

| Role | Where | Model · effort |
|---|---|---|
| **Conductor** (live session) | orchestrates; decompose + oracle in-session | your session model — not forced; two-way nudge |
| **Per-unit subprocess** (plan+execute) | Loop 1 worktree | Fable (≥ 0.5) / Opus · xhigh (0.2–0.5) / Sonnet · xhigh (< 0.2) |
| **Planner** | inside the unit | Fable · high (≥ 0.5), else Opus · high |
| **Scout / research** | inside the unit, reads files | Sonnet · low (Haiku trivial) |
| **Code review** | fresh context | Opus · high |
| **Verifier / Tester** | verify | Haiku · low |
| **Conflict resolver** | Loop 2 | Opus · high |
| **Loop-2 fix** | Loop 2 | Sonnet · medium |

**Principle:** Fable only where reasoning-leverage is high and token-volume low; hard units (≥ 0.5) build on Fable automatically by difficulty; the scout never reads on Fable, and review is a fresh Opus.

- **Brief a past session for the next one (`/bgsd-generate-brief`).** A new history/utility command that synthesizes a clean, comprehensive markdown brief of a completed session (what was requested, what was done per unit, the agents, what changed, outstanding items, and a ready-to-paste "how to continue" `/bgsd-sesh` line) and writes it to `.bgsd/briefs/<run-id>-brief.md`. Defaults to the last session; pass a `<run-id>` for a specific one. The narrative synthesis runs on Sonnet (cheap summarization, no Fable/Opus) and is read-only over history — it never modifies past records. See [`/bgsd-generate-brief`](./commands-reference.mdx#bgsd-generate-brief).
- **The dashboard opens on its own.** The `--gui` web dashboard now opens automatically for feature- and project-scale sessions (never for quick fixes), so you get the full-pipeline view without asking. Controlled by the new `gui.auto` knob in `BGSD.md` (default `true`); `--no-gui` suppresses it for a session, and `--gui` forces it on even for a quick fix. It also no longer flickers or re-animates on its ~1.5s refresh: the page only re-renders when the run state actually changes.
- **Walk-away notifications.** When a pipeline unit parks and needs your input (a `needs_input` escalation), the Conductor now fires a native macOS notification, so you can step away from the terminal and still get pinged. Opt out with the new `notifications.os` knob in `BGSD.md` (default `true`). macOS only; a silent no-op everywhere else.
- **Kiwi always tells you why it sized the job the way it did.** Every session now prints a one-line explanation of the scale decision (e.g. "auto-scaled to feature — route 'multi-file', ~3 units, 2 surfaces, length band medium"), so the auto-scale is never a black box. Forced scale (via `--quick` / `--feature` / `--project`) and clarify-instead-of-guess cases are narrated the same way.
- **Prune merged branches and worktrees (`/bgsd-clean`).** A new maintenance command that removes merged bgsd branches and their stale git worktrees. It is plan-first (it shows exactly what it will remove; `--dry-run` and `--json` give you a preview), only ever touches `bgsd-`-prefixed branches, and hard-protects `next` / `main` / `master` and the current branch. `--force` includes unmerged bgsd branches but still never touches a protected one. See [`/bgsd-clean`](./commands-reference.mdx#bgsd-clean).
- **Lossless resume after compaction.** `/bgsd-resume` now reads a structured compact-handoff sidecar (`.bgsd/runs/<id>/compact-handoff.json`: stage, wave, per-agent phase/status, pending gates, next step). If a session was compacted or interrupted, resume surfaces that handoff first and picks up exactly where it left off, then consumes the handoff so it is never replayed.
- **Name your Conductor at `/bgsd-init`.** First-time setup now asks — with arrow-key selectors — for your Conductor's **name** and **emoji** (default 🥝 Kiwi, or type your own). Both persist to `BGSD.md` (`conductor.name` / `conductor.emoji`) and flow everywhere the Conductor shows itself: the chat name pill, the live status banner and narration, and the web dashboard header. Change either any time by editing `BGSD.md`, via `/bgsd-modify-memory` ("rename yourself to Jarvis", "change your emoji to 🤖"), or just by asking the Conductor.
- **The Conductor self-manages its own context.** The human-facing Conductor now watches its own context window and, at `conductor.self_compact_at` (default 90%), writes a handoff note and auto-compacts to keep a long session running to completion instead of dying mid-pipeline. Tune it in `BGSD.md`.
- **Neumorphic dashboard with clickable cards.** The `--gui` dashboard was restyled to a soft neumorphic aesthetic, and every agent card is now clickable: open it for the full, untruncated detail (the complete note, GSD flow, phase, iteration, and progress) in a live-updating panel.
- **The full pipeline now actually runs.** As of 0.5.0, a plain `/bgsd-sesh` fires the entire two-loop pipeline end-to-end with zero friction. The old `--live` human-gate on the execution path itself is gone; only the `main`/`master` branch guard remains. Nothing writes to `main`.
- **Per-unit GSD tailoring.** Each Loop-1 Pipeline Agent now runs a per-unit-tailored GSD flow in its own git worktree. The Conductor decides which GSD phases each unit gets: research on harder units, `/gsd-ui-phase` for UI units, `/gsd-ai-integration-phase` for AI units, a code-review gate on harder work. Trivial/quick units skip GSD phases and apply a direct fix. This is driven by the new `/bgsd-run-agent` command and `phaseconfig.mjs` resolver.
- **Decision oracle (proxy Q&A).** The Conductor answers GSD's discuss-phase questions as the user's proxy via the decision oracle (new `oracle.mjs --answer` CLI). Only true unknowns escalate, non-blockingly, per unit.
- **Gradient session banners.** Oh-my-logo gradient banners now print at session start, between each stage, at finish, and on init.

- **The backlog (start with no prompt).** Run `/bgsd-sesh` with no prompt and the Conductor proposes the next item from a persistent backlog (the queue at `.bgsd/queue/queue.json`). When you defer scope mid-session ("scope this later"), the Conductor enqueues it instead of dropping it, and at the end of every session it proposes the next item. Work drains across sessions without re-typing. New queue subcommands `peek` and `done` back the loop. See [/bgsd-queue](./bgsd-queue.mdx).
- **Execution modes (`--mode` / `--verify-mode`).** Pipeline agents and verifiers each run in one of three modes: `fast` (skip research; code-only quick checks), `thorough` (research every unit; full driver ladder), or `adaptive` (the default: the Conductor decides per unit). Override per-session with `--mode fast|thorough|adaptive` (pipeline) and `--verify-mode fast|thorough|adaptive` (verifiers), or persist under `modes` in `BGSD.md`.
- **Role-aware model routing and branded subagents.** Each role gets a model and effort by the doctrine above (per-unit subprocesses build on `sonnet/xhigh` below difficulty 0.2, `opus/xhigh` from 0.2–0.5, and a whole Fable subprocess at ≥ 0.5; scouts run cheaper than that; verifiers run `haiku/low`). Every subagent is spawned with a consistent branded label of the form `<emoji> <Role> · <unit> (<model>)` so you can tell each agent's role and model at a glance.
- **Headless UI (`--headless-ui`).** Runs Playwright headless, with no visible browser or server window popping up on your machine (discreet). Orthogonal to `--no-usage-verification`; persist as `verification.headless` in `BGSD.md`.
- **Selector questions.** Every question the Conductor asks (a vague prompt to clarify, a gray-area decision, the review gate, "which backlog item next") is a GSD-style arrow-key selector with a hard maximum of 4 concrete options plus an always-available "type your own", never a wall of prose.
- **Per-subagent context management.** Each worktree Pipeline Agent runs in its own large (~1M-token) window. The Conductor watches each agent's usage and proactively compacts it (default at 0.70 of the window) or relaunches it from a handoff manifest (default 0.90) before it overflows. Tune it with the `context` block in `BGSD.md`.
- **Verification depth (`--no-usage-verification`).** The goal-backward code verification (the gsd-verifier) always runs. The heavier Playwright usage testing (driving the real app) is now optional: turn it off per-session with `--no-usage-verification`, per-repo with the `verification.usage_testing` knob in `BGSD.md`, or just tell the Conductor ("stop UI-testing quick fixes") and it edits the setting itself. Good for quick fixes and non-UI changes; it never disables code verification. See [/bgsd-verify](./bgsd-verify.mdx).
- **Modify settings in plain language (`/bgsd-modify-memory`).** Tell the Conductor what to remember for this repo ("always verify headless", "default the pipeline to thorough") and it writes the exact `BGSD.md` knob, or appends a free-form preference to the Notes section. A flag you type on a specific session always overrides a remembered setting: **flag > BGSD.md > default.**
- **Search past session history (`/bgsd-recall`).** Ask Kiwi what happened in previous sessions ("what did we build last month?", "what changed in the auth layer?") and get a conversational answer with concrete facts: what shipped, when, and which run id. Read-only; never modifies any record.
- **Resume an interrupted session.** If a session is cut short (the Claude Code instance is lost), `/bgsd-resume` finds the most recent in-flight run under `.bgsd/runs/` and picks it back up from each unit's last phase; `/bgsd-resume <run-id>` targets a specific one.
- **The name pill, splash, and terminal identity.** Every conversational message the Conductor sends is prefixed with a name pill — `🥝 Kiwi:` by default (the name is customizable in `BGSD.md`) — a colored Markdown badge in front of each message, so you always know the Conductor is speaking. A session opens with the splash banner and, right after it, a terminal `/rename` (an apt task name) plus a random `/color`, so parallel sessions are easy to tell apart. Structured outputs (verdict lines, report JSON) stay literal.
- **The live dashboard (`--gui`).** Pass `--gui` (or say "open the dashboard") and the Conductor opens a local web view that tracks every agent live: the parallel Loop 1 Pipeline Agents, the Verification lane, the Loop 2 Integrator, and the Review Gate, each card showing the agent's GSD substage, status, and progress, with per-agent GSD-flow steppers, a pipeline-stage timeline, and a sessions tab. It reads the run's control files, refreshes on its own, and the Conductor can open or close it at any point (the `/bgsd-gui` command). The terminal narration already keeps things legible for most runs; the dashboard gives you an animated full-pipeline view when you are running many agents at once and want unparalleled visibility into every agent's state at a glance.
- **`--fable` (largely superseded).** The flag is now mostly redundant: hard units (difficulty ≥ 0.5) already route their whole per-unit worktree subprocess to **Claude Fable 5** by difficulty, so you rarely need to ask. `--fable` nudges the difficulty threshold so more units qualify, but it can't put the Conductor or any in-session subagent on Fable (the agent tool is opus/sonnet/haiku only, and bgsd never forces your session model). You can also just tell the Conductor to run any specific unit on Fable — or drop it — conversationally, with no restart.

## Internal stage references

These pages document what the Conductor runs internally. You never call these commands directly from a `/bgsd-sesh` — the Conductor orchestrates all of them. They are reference material for contributors, advanced users, and anyone who wants to understand the mechanics.

### v0 — Verify engine

- **[/bgsd-verify reference](./bgsd-verify.mdx)** — Full reference for the verify stage: arguments, acceptance-criteria input formats (`--criteria` file or `--inline` string), the `verification-report.json` schema (all fields and types), and detailed driver-ladder behavior (pre-flight probe, rung-by-rung procedure, `console_reliable` flag, and hard rules).

### v1 — Fix-stream

- **[/bgsd-queue reference](./bgsd-queue.mdx)** — Fix-stream lifecycle diagram, state machine (all states and terminal conditions), subcommands, classification rules and routing table, Loop 1 controller algorithm and stop conditions, queue store format.

- **[Hyperpolymath capture→queue cron](./hyperpolymath-capture.mdx)** — How bgsd turns Hyperpolymath items into queue entries: the capture seam contract, dry-run cron invocation modes, idempotency via content-key dedup, launchd scheduling, and the human-gated live hookup.

### v2 — Conductor pipeline

- **[/bgsd-run reference](./bgsd-run.mdx)** — The Conductor state machine: decomposition and the verified DAG, topological wave ordering, control-file protocol and heartbeat/restart, worktree fan-out and wave scheduler, conflict pre-check and merge-resolver, integration onto the standing `next` branch, doc aggregation, reversible cleanup, context management, and the human-gated `--live` checklist.

- **[/bgsd-status reference](./bgsd-status.mdx)** — The Conductor's live status view: color-coded per-worktree badges, the worker table layout, merge history, budget and context telemetry (tokens, cost, pressure level), `--watch` live refresh, `NO_COLOR`/non-TTY behavior, and the `main-protected` indicator (marking that `main` is never written by an agent).

### v3 — Integration loop + human handoff

- **[/bgsd-integrate + /bgsd-user-eval reference](./bgsd-loop2-review.mdx)** — Loop 2 integration verify→fix on the standing `next` branch: boot the integrated app, run the Integration Tester, dispatch parallel fix agents, re-merge, and re-verify in a bounded loop until clean or a stop condition fires. Followed by the User Review Gate: auto-boot `next`, per-criterion checklist, GSD-style selector verdict (approve / request-changes / abort / type-your-own), `review.json` output, and the never-auto-pass rule.

- **[/bgsd-feedback + CHANGELOG→PR reference](./bgsd-feedback-changelog.mdx)** — Feedback mode ingestion and routing: full re-run of both loops on your findings vs `--fast` parallel fix agents with no verification (always `UNVERIFIED`). Per-agent CHANGELOG aggregation across Loop 1, Loop 2, and feedback rounds. PR body assembly as a pure deterministic string. Guarded `gh pr create` into `next` behind `--live`, with the agents-never-write-to-`main` rule (the guard refuses `main`/`master` as PR base) enforced unconditionally.

These pages render standalone without any nav config change. When a maintainer is ready to surface all bgsd pages in the nav, add one group entry to the Mintlify nav config (`mint.json` or `docs.json`):

  "group": "bgsd",
  "pages": [
    "bgsd/docs/conductor-session",
    "bgsd/docs/commands-reference",
    "bgsd/docs/quickstart",
    "bgsd/docs/bgsd-verify",
