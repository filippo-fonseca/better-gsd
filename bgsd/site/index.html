§ 02  ·  The Core Value

The make-or-break test.

An agent that boots your app, checks it against acceptance criteria, and returns a reliable, structured defect list — including catching the console errors a screenshot alone would miss.

🔎
Console-first verification

The driver ladder checks console messages before it ever looks at the DOM or takes a screenshot. React's validateDOMNesting warnings, hydration mismatches, and missing-key errors all fire at console level — invisible to visual regression tools. bgsd surfaces them.

Rung 1 of 4
📈
Structured defect reports

Every run writes a schema-validated verification-report.json: per-criterion pass/fail, defect list with severity and source rung, screenshot index, and a driver-ladder audit. Machine-readable. Actionable. No ambiguity.

REPORT-01..03
🔄
Verify-then-fix loops

v1 introduced Loop 1: after execution, bgsd verifies and, on defects, re-routes to GSD for a fix. The loop runs up to 5 iterations with escalating model effort. A pass is only recorded on a verified Tester PASS. Never a silent green.

v1 Loop 1
🌟
Kiwi, the Conductor

v2's Conductor (codename Kiwi) decomposes a large prompt into a DAG of parallel GSD units, fans them across isolated git worktrees, conflict-checks and merges verified branches, and checkpoints to you at every wave boundary. Your production branch is never touched.

v2 Conductor
🔒
No silent green — ever

If the Playwright MCP is absent, bgsd emits BLOCKED — not a fabricated PASS. If evidence is insufficient, verdict is INSUFFICIENT_EVIDENCE. Every non-clean stop produces a structured terminal state. This invariant is enforced in code, not just aspirationally documented.

NFR-06
🔧
Additive, never destructive

bgsd lives under bgsd/. It never edits vendored GSD directories (commands/, agents/, gsd-core/, etc.). It reaches GSD only through three stable seams: /gsd-* slash commands, the .planning/ file contract, and config.json.

NFR-01..04

§ 03  ·  How It Works

The four-rung driver ladder.

Cheapest and most reliable first. Vision is a last resort, not a crutch.

1
Console messages
Most bugs die here

browser_navigate then browser_console_messages. Timing is critical: navigate first so the MCP buffer captures React render-time warnings. This rung caught the validateDOMNesting defect in the canary proof.

2
Network requests
Surface 4xx / 5xx silently swallowed

browser_network_requests. Flags any response where ok === false or status ≥ 400 for a required resource. Analytics beacons are noted but not automatically treated as failures.

3
DOM snapshot
Semantic structure, not pixels

browser_snapshot after domcontentloaded. networkidle is explicitly prohibited (DRIVER-04) — apps with WebSockets or analytics beacons can hang indefinitely. Semantic selectors (roles, labels, headings) verify rendered content against criteria.

4
Vision (fallback only)
Last resort for purely visual criteria

browser_take_screenshot. Fires only when rungs 1–3 cannot decide a criterion. Vision tokens are expensive and screenshots are blind to console and network defects. bgsd uses them last, not first.

Pre-flight MCP probe

Before any acceptance criterion is touched, bgsd calls browser_snapshot as a no-op reachability check. If the MCP is absent, the run halts immediately:

{
  "verdict": "BLOCKED",
  "reason": "mcp_unavailable",
  "install_guidance":
    "claude mcp add playwright ..."
}

No result is fabricated. This is the "no silent green" invariant.

Verdict stdout contract

The only thing that reaches stdout is a single verdict line. The full JSON report lands on disk, never in the terminal.

PASS  .bgsd/runs/<run-id>/verification-report.json
FAIL  .bgsd/runs/<run-id>/verification-report.json
ERROR  .bgsd/runs/<run-id>/verification-report.json

§ 04  ·  Command Surface

Five slash commands.

From a single verify call to a full Conductor-orchestrated project run — all in the Claude Code chat.

/bgsd-verify
v0  ✓ proven

Boot or attach to a running app and verify it against acceptance criteria. Returns a single verdict line + a structured verification-report.json. The make-or-break command: if the driver ladder can't drive a real browser, it emits BLOCKED, never a fabricated pass.

/bgsd-queue
v1  ✓ built

A persistent fix-stream. Add items with bgsd-queue add; drain them with bgsd-queue start. Each item moves through classify → route → execute → verify → loop until it reaches a terminal state. Durable store, content-key dedup, append-only audit trail.

/bgsd-run
v2  ✓ built

The Conductor (Kiwi). Takes one large prompt, decomposes it into a verified DAG, fans units across parallel git worktrees, runs Loop 1 per worktree, conflict-checks and merges verified branches, and checkpoints at every wave boundary. Default is --dry-run; the live path requires explicit --live.

/bgsd-status
v2  ✓ built

The Kiwi live status view. Color-coded per-worktree badges, Loop 1 iteration counts, merge history, budget and context telemetry, and the 🔒 main-protected indicator. Zero model calls. Supports --watch for live refresh.

/bgsd-capture
v1  ✓ built

The Hyperpolymath capture adapter. Fetches external Hyperpolymath items and enqueues them into /bgsd-queue. Default path is completely safe: dry-run, mock source, zero credentials required. The live hookup is human-gated behind --live.

§ 05  ·  Milestones

Proven in order. Built to deepen.

Each version de-risks the next. The core value was validated at v0, before any orchestration was built on top of it.

✓
v0  —  Milestone 1  ✓ PROVEN
Standalone Tester + /bgsd-verify

The make-or-break test, proven in isolation. /bgsd-verify against a Next.js canary returned FAIL on a <div>-in-<p> defect (a real React console error invisible to a screenshot) and PASS on the clean route, reproducibly across reruns. The tester, runtime-isolate, criteria parser, report assembler, and schema are all live.

✓
v1  —  Fix-stream  ✓ BUILT
/bgsd-queue + Loop 1

Persistent fix-stream with classify → route → execute → verify → loop. Queue, classify-item, route-item, and loop1 scripts with 85 unit tests across all four layers. The two live runs (Loop 1 autonomous spawn, Hyperpolymath cron) are guarded behind --live and remain human-gated.

✓
v2  —  Conductor  ✓ BUILT
/bgsd-run (Kiwi) + /bgsd-status

Full Conductor pipeline: decomposition, dependency graph, worktree fan-out, wave scheduler, conflict pre-check + merge-resolver, rehearsal assembly, doc aggregation, reversible cleanup, context management, and the /bgsd-status live view. 14 test suites green across v0+v1+v2. Live multi-process run is human-gated behind --live.

v3  —  Loop 2 + User Review Gate  · Planned
/bgsd-user-eval + /bgsd-feedback

Integration verify→fix (Loop 2), per-agent CHANGELOG into the PR, user review gate at the end of a Conductor run, and feedback mode for rapid iteration on a specific defect.

v2-intake + v4 Remote  · Planned
Intake/proxy extension + remote orchestration

Intake extension (E1–E6) drafted in .planning/v2-intake/. Remote orchestration (off-machine worktrees, distributed execution) planned for v4.

§ 06  ·  Installation

Three commands to first verify.

Install bgsd

Run from the repo root where bgsd/ lives. bgsd loads as a second plugin via a local marketplace — GSD's own plugin manifest is never touched.

Step 1 — Register and install the plugin
# Register the local marketplace source
claude plugin marketplace add ./bgsd

# Install the bgsd plugin (user scope)
claude plugin install bgsd@bgsd-local
Step 2 — Add Playwright MCP
# Add once per machine — pinned version
claude mcp add playwright -- npx @playwright/mcp@0.0.76
Step 3 — Restart Claude Code, then run the canary proof
# Boot the canary fixture and verify the clean route (expect PASS)
/bgsd-verify --boot bgsd/fixtures/canary-next \
             --criteria bgsd/fixtures/canary-next/acceptance.md

# Verify the buggy route (expect FAIL on validateDOMNesting)
/bgsd-verify http://localhost:<port>/buggy \
             --criteria bgsd/fixtures/canary-next/acceptance.md

The /buggy route looks identical to a working page in a screenshot. The defect only exists in the browser console. That is exactly what bgsd catches. Run the fixture in development mode: React's validateDOMNesting warning is stripped from production builds.

§ 07  ·  Hard Rules

Enforced, not aspirational.

These invariants are checked in code. bgsd will tell you clearly when one is about to be violated.

Invariant Enforcement
Never write to next / main All work lands on feat/bgsd-v0 or other non-default branches. No automated push or PR to the default branch, ever.
Additive only bgsd lives under bgsd/ (plus runtime .bgsd*/ dirs). It never edits GSD's directories.
Never edit vendored GSD The forked GSD source (commands/, agents/, gsd-core/, skills/, hooks/) is read-only to bgsd.
Seams only bgsd reaches GSD only through (1) /gsd-* slash commands, (2) the .planning/ file contract, and (3) config.json. No reaching into GSD internals.
No silent green (NFR-06) If evidence is insufficient: INSUFFICIENT_EVIDENCE, not PASS. If MCP is absent: BLOCKED. Every non-clean stop produces a structured terminal state.
Bounded, reversible autonomy (NFR-08) Every loop is bounded by max_iterations; every Conductor run is bounded by --budget-cap; every wave requires your go/no-go. Cleanup writes a recovery file before deleting anything.
Live runs are human-gated Live multi-process orchestration and live Hyperpolymath capture both require an explicit --live flag. The guard checks process.argv — not environment variables — and throws a detailed refusal if absent.
