# Requirements: better-gsd (bgsd) — Milestone 4 (v3)

**Defined:** 2026-06-29
**Core Value (v3):** The second half of the two-loop machine and the human handoff. After v2 assembles a `rehearsal/<run-id>` integration branch and checkpoints, v3 runs **Loop 2 — an integration verify→fix loop over the whole assembled app** (boot the integrated system, run the v0 Tester end-to-end across feature boundaries, and on integration defects spawn fix agents → re-verify in a bounded Ralph loop until clean or a stop condition), then hands the result to a **User Review Gate** — `/bgsd-user-eval` boots the rehearsal servers and prints a localhost URL + a per-criterion checklist, and an interactive GSD-style selector Q&A captures the human go/no-go. A **`/bgsd-feedback "<what's wrong>" [--fast]`** mode feeds the human's findings back into the system (full path re-runs both loops on the feedback items; `--fast` skips the loops and just spawns parallel fix agents / a single agent with no computer-use verification). Finally, the per-agent CHANGELOG that v2 generated into the run ledger is **aggregated and wired into a real PR description** — the PR targeting a non-default branch, human-gated, never `next`.
**Milestone:** Milestone 4 = v3 only (Loop 2 integration loop + User Review Gate + `/bgsd-user-eval` + `/bgsd-feedback [--fast]` + per-agent CHANGELOG-into-PR). Builds directly on the v0 Standalone Tester, the v1 Loop 1 / Ralph controller pattern, and the v2 Conductor (`rehearsal/<run-id>` assembly, run lifecycle state machine, doc aggregation + CHANGELOG seed, live status view). It deliberately EXCLUDES the intake/proxy extension (`.planning/v2-intake/`) and v4 remote-control.
**Plan source:** `BETTER-GSD-DOCS/better-gsd-plan.md` — Part 5 Loop 2 (integration verify→fix mechanics), Part 7 (`/bgsd-user-eval`, `/bgsd-feedback [--fast]` command surface), Part 1 §10–11 (user evaluation abstracted to the rehearsal branch + per-subagent changelog into the PR; feedback mode), Part 8 v3 (build-sequence subsection), Part 6 (CHANGELOG → PR body & user eval). Routing/effort from Part 11 (Integration Tester = Opus/xhigh, fix agents = Sonnet/medium, `--fast` = Haiku/Sonnet/low, doc aggregation = Haiku/low). Token doctrine from Part 13 §9 (don't re-verify the unchanged — scope Loop 2 to the merged diff). Risks from Part 9 §1, §3.

## Non-Functional Constraints (Hard Rules — enforced, not aspirational)

These apply to every v3 requirement and must hold at all times. NFR-01..09 are inherited unchanged from v0/v1/v2; v3 adds NFR-10 (the live integration run and real PR creation are human-gated) and NFR-11 (the User Review Gate is interactive-by-design — a human gate, never auto-passed).

- [ ] **NFR-01 (Branch safety)**: bgsd never writes, commits, pushes, or opens a PR to the default/production branch (`next`). Loop 2 fixes land only on worktree branches off `rehearsal/<run-id>` and on `rehearsal/<run-id>` itself; the per-agent CHANGELOG PR is opened against a NON-default branch only, never `next`. Only the human merges `rehearsal/<run-id>` → `next`, by hand. A guard hook rejects any automated write/PR to the default branch. (Plan Part 1 §9, Part 2, Part 4.)
- [ ] **NFR-02 (Additive code)**: All v3 source lives under the existing `bgsd/` namespace (new `loop2.mjs` / `loop2-live.mjs`, `review.mjs`, `feedback.mjs`, `changelog-pr.mjs` / `changelog-pr-live.mjs`, plus `commands/bgsd-user-eval.md` and `commands/bgsd-feedback.md`) and `.bgsd*` runtime dirs (`runs/<id>/integration.md`, `integration-report.json`, `review.json`, `feedback/`). bgsd never adds files into GSD's own directories in a way that changes GSD behavior. (Plan Part 1 §1, Part 6, Part 10.)
- [ ] **NFR-03 (Never edit vendored GSD)**: The forked GSD source (root `commands/`, `agents/`, `gsd-core/`, `skills/`, `hooks/`, `.claude-plugin/plugin.json`, root `.gitignore`, root `docs/`, `src/`) is read-only to bgsd. bgsd makes zero edits to it; Loop 2 fix agents drive GSD only through `/gsd-*` and the config seam. (Plan Part 2, Part 12.)
- [ ] **NFR-04 (Seams only)**: bgsd touches GSD only through three stable seams — (1) GSD's `/gsd-*` slash commands, (2) the documented `.planning/` file contract, (3) `config.json` / per-worktree `model_overrides`. Loop 2 reuses the v0 Tester via the same command/report seam; feedback re-routes through the v1/v2 classify→route seam. No reaching into GSD internals. (Plan Part 1 §1, Part 11, Part 12.)
- [ ] **NFR-05 (Scripts over models / capture-then-summarize — "rule zero")**: The Loop 2 controller (poll, iteration accounting, stop-condition logic, defect-signature no-progress detection), the integrated-app boot/teardown, the merged-diff scoping, the git operations behind fix-agent re-merge, the review-gate state machine + selector rendering, feedback ingestion/parsing/routing, and the CHANGELOG aggregation + PR-body assembly are deterministic scripts — never a model. Only the high-stakes judgment points (the Integration Tester verdict, a fix agent, classifying a feedback item) call a model, and they get only their failing slice / relevant excerpt — never the whole run. (Plan Part 11 "rule zero", Part 13 §1–6 + §9.)
- [ ] **NFR-06 (No silent green)**: When the integrated app cannot be truly verified (Integration Tester emits `BLOCKED`/`ERROR`/`UNRELIABLE`, the rehearsal app won't boot, MCP unavailable, or Loop 2 exhausts `max_iterations` without a clean integration pass), Loop 2 ends in a structured non-PASS terminal state (`integration_failed`/`integration_blocked`) with the `integration-report.json` path attached — never a fabricated clean integration. The User Review Gate is never auto-passed (NFR-11): an unanswered gate parks the run in `needs_input`, never `done`. A feedback re-run that can't verify ends non-PASS, same as Loop 1/2. (Plan Part 5 §5, Part 9, v0/v1/v2 NFR-06.)
- [ ] **NFR-07 (Conductor is the only automated→human interface)**: Loop 2 fix agents, the Integration Tester, and feedback fix agents never prompt the user directly; they write to control/report files the Conductor reads. The User Review Gate is the ONE place the run intentionally stops for the human, and it speaks through the Kiwi channel with exactly one consolidated review prompt (URL + checklist + selector). Feedback enters through `/bgsd-feedback`, not by addressing an agent. (Plan Part 1 §5 + §10, Part 2, Part 3 §2–3.)
- [ ] **NFR-08 (Bounded, reversible autonomy)**: Loop 2 is bounded by a configurable `max_iterations` and exits cleanly on any stop condition; feedback re-runs (full and `--fast`) are equally bounded; the per-run budget cap downshifts only non-critical layers (effort first, then model) and never the integration verdict (Part 11 forbids downshifting the integration verdict). The Conductor keeps the v2 merge-boundary checkpoints AND adds the User Review Gate as a mandatory human stop — v3 does NOT promise fire-and-forget (relaxing checkpoints toward walk-away is DEF-23, deferred). (Plan Part 5 §5, Part 8 v3, Part 9 §3, Part 11 budget.)
- [ ] **NFR-09 (Context never overflows)**: Loop 2 reuses the Conductor's pointers-not-blobs discipline — the controller holds only small control/report/ledger files; the Integration Tester gets the merged-diff slice + the requirements excerpt, not the whole app; each fix agent gets only its tagged integration item; feedback fix agents get only their feedback slice. Loop 2 scopes integration testing to the merged diff + feature-interaction surface, not the whole app on every iteration (Part 13 §9), so context (and cost) stay bounded across iterations. (Plan Part 13 §2–4 + §9, PROJECT.md DEF-10/DEF-22.)
- [ ] **NFR-10 (Live integration run + real PR creation are human-gated)**: The real end-to-end Loop 2 run (booting the actual `rehearsal/<run-id>` app and driving real Integration-Tester→fix cycles) and real PR creation (`gh pr create` against a non-default branch with the CHANGELOG body) are built + unit-tested in isolation behind injected boundaries / mocked git+gh first, then exercised only via an explicit, off-by-default `--live` opt-in, human-supervised, never in automated CI, never writing `next`. A `--dry-run` path prints the would-be integration plan / the would-be PR (title + body + base branch) and exits without booting or pushing anything. (Plan Part 8 v3, Part 9 §1, NFR-08; mirrors v1 Phase 3 / v2 Phase 4 live-run criteria and the `loop1-live.mjs` / `run-live.mjs` `requireLiveFlag()` pattern.)
- [ ] **NFR-11 (User Review Gate is interactive-by-design)**: The User Review Gate is a human gate, not an automatable check — it is interactive by design and never auto-passes. It uses GSD-style selector Q&A (pre-filled choices the human can pick, plus a type-your-own option) so the human's verdict (approve / request changes / abort) and any free-text findings are captured structurally. The gate state machine is deterministically unit-testable with an injected prompt function (a mock answer in tests; the real interactive prompt under the live/interactive path); the actual human interaction is never simulated away as a pass. (Plan Part 1 §10, Part 7 `/bgsd-user-eval`, GSD selector-Q&A convention, NFR-06/07.)

## v3 Requirements (this milestone)

Requirements for the v3 release. Each maps to exactly one roadmap phase. Grouped by area: LOOP2 (integration verify→fix loop), REVIEW (User Review Gate + `/bgsd-user-eval`), FEEDBACK (`/bgsd-feedback [--fast]`), CHANGELOG (per-agent CHANGELOG into the PR), plus DOCS. The bulk is buildable + unit-testable deterministically with **mocked Tester/fix/git/gh boundaries** (reusing the v1 `loop1.mjs` injected-`verify`/`fix` pattern and the v2 `*-live.mjs` `requireLiveFlag()` guard); the live integration run and real PR creation are isolated into human-gated criteria.

### Loop 2 — Integration Verify→Fix (LOOP2)

- [ ] **LOOP2-01**: After v2 assembles `rehearsal/<run-id>` and clears its merge-boundary checkpoint, the Conductor advances the run into an `integrating` lifecycle state and runs Loop 2 over the WHOLE assembled app: it boots the integrated `rehearsal/<run-id>` instance (reusing the v0 `runtime-isolate.sh` convention, one integrated server, not per-worktree) and spawns the **Integration Tester** against it. Loop 2 runs on the integrated system, not a single worktree — it is the integration-level sibling of v1 Loop 1. (Plan Part 5 Loop 2 §1–2, Part 8 v3.)
- [ ] **LOOP2-02**: The Integration Tester reuses the v0 Tester end-to-end and emits a structured **`integration-report.json`** that reuses the v0 report contract (`verdict` ∈ `PASS|FAIL|ERROR`, `criteria_results`, `defects` with severity/source/evidence) and adds integration-specific scrutiny: end-to-end UAT across feature boundaries, a code review of the integrated diff, an alignment check against the original prompt/requirements, and active scrutiny for improvements (feature-interaction smells, polish, consistency — not only regressions), each item tagged to a file/feature. The verdict is computed by the v0 `computeVerdict()` contract reused unchanged. (Plan Part 5 Loop 2 §2–3, Part 11 "Integration Tester = Opus/xhigh", reuses v0 REPORT/verdict.)
- [ ] **LOOP2-03**: On a non-clean integration verdict, the defects/recommendations become a backlog and the Conductor spawns **parallel fix agents** (Sonnet/medium per Part 11) in worktrees branched from `rehearsal/<run-id>`, each fixing one independent tagged item, then re-merges into `rehearsal/<run-id>` (reusing the v2 conflict pre-check + dependency-ordered merge for the re-merge), and the Integration Tester re-runs — verify→fix→re-verify, a Ralph-style loop at the integration layer. The Loop 2 controller is the v1 `runLoop1`-shaped controller reused at integration scope: the `verify` (Integration Tester) and `fix` (parallel fix-agent batch) boundaries are dependency-injected so the whole controller is unit-testable under mocked Tester/fix. (Plan Part 5 Loop 2 §4, Part 11 fix-agent row, reuses v1 `loop1.mjs` DI shape + v2 `conflict.mjs`.)
- [ ] **LOOP2-04**: Loop 2 repeats until the Integration Tester returns `PASS` (clean → advance to the User Review Gate) OR a stop condition fires — `max_iterations` reached, no-progress detected (recurring integration-defect signature, reusing the v1 `defectSignature()` no-progress logic), or a `BLOCKED`/`ERROR` verdict — at which point the run parks in a structured non-PASS terminal state (`integration_failed`/`integration_blocked`) with the `integration-report.json` path attached and the integration log written to `.bgsd/runs/<run-id>/integration.md`. Each iteration count and stop reason is recorded; spend stays bounded (NFR-08) and scoped to the merged diff (NFR-09, Part 13 §9). Never a fabricated clean integration (NFR-06). (Plan Part 5 Loop 2 §5, Part 9 §3, Part 13 §9, reuses v1 stop-condition logic.)
- [ ] **LOOP2-05 (HUMAN-GATED live integration run)**: The real end-to-end Loop 2 run — actually booting the `rehearsal/<run-id>` app with real servers and driving real Integration-Tester→fix cycles to a clean integration — is built + unit-tested in isolation behind mocked Tester/fix first (LOOP2-03), then exercised only via an explicit, off-by-default `--live` opt-in (`loop2-live.mjs` with the same `requireLiveFlag()` guard as `loop1-live.mjs`/`run-live.mjs`), human-supervised, never in CI, `next` never written. A `--dry-run` default prints the integration plan (what would boot, the merged-diff scope, the would-be Tester invocation) without booting or fixing anything. (Plan Part 8 v3, Part 9 §1, NFR-10; mirrors v1 LOOP Phase 3 + v2 SPAWN-04 live criteria.)

### User Review Gate + `/bgsd-user-eval` (REVIEW)

- [ ] **REVIEW-01**: When Loop 2 returns clean, the Conductor advances the run into a `review` lifecycle state and opens the **User Review Gate** — the one mandatory human stop in v3 (NFR-11), abstracted to the `rehearsal/<run-id>` branch per Part 1 §10. The gate surfaces, through the Kiwi channel, exactly one consolidated review prompt: what the run built (the per-agent CHANGELOG summary), the localhost URL from `/bgsd-user-eval`, and the integration test checklist. (Plan Part 1 §10, Part 5 Loop 2 §6, Part 7.)
- [ ] **REVIEW-02**: `/bgsd-user-eval` auto-boots the servers/backend for `rehearsal/<run-id>` (reusing the v0/v2 `runtime-isolate.sh` boot/readiness/teardown convention against the integrated instance) and prints the localhost URL plus a concrete, human-readable test checklist derived from the run's acceptance criteria + the `integration-report.json` — so the human can click through and verify by hand. Boot/readiness/teardown is a deterministic script (NFR-05); the live boot of the real rehearsal app is human-gated under the same `--live`/`--dry-run` discipline as Loop 2 (NFR-10). (Plan Part 7 `/bgsd-user-eval`, Part 1 §10, reuses v0 ISO.)
- [ ] **REVIEW-03**: The review gate captures the human's verdict via **GSD-style selector Q&A** — pre-filled choices (`approve` / `request changes` / `abort`) the human picks plus a type-your-own free-text field for findings — written to a structured `.bgsd/runs/<run-id>/review.json` (verdict, free-text findings, timestamp). The gate state machine is deterministic with the interactive prompt dependency-injected, so it is unit-testable with a mocked answer (NFR-11); `approve` advances the run toward the CHANGELOG/PR step, `request changes` routes the findings into `/bgsd-feedback`, `abort` parks the run, and an un-answered gate parks in `needs_input` — never auto-passed (NFR-06). (Plan Part 1 §10, GSD selector-Q&A convention, NFR-11.)
- [ ] **REVIEW-04**: The User Review Gate is surfaced in the live `/bgsd-status` view (reusing the v2 `status.mjs` renderer): a distinct `review` / `needs-input` badge and a Kiwi "needs your eval" prompt line so the human always sees when a run is parked at the gate, consistent with the v2 always-on status discipline and the 🔒 main-protected indicator. The view path stays zero-model (NFR-05). (Plan Part 16, Part 7, reuses v2 STATUS surface.)

### Feedback Mode — `/bgsd-feedback [--fast]` (FEEDBACK)

- [ ] **FEEDBACK-01**: `/bgsd-feedback "<what's wrong>"` ingests the human's free-text feedback (or the structured findings from a `request changes` review verdict) and parses it into a set of discrete, traceable feedback items written under `.bgsd/runs/<run-id>/feedback/` — a deterministic ingestion/parse step (NFR-05) that tags each item to a file/feature where possible and assigns it a stable id, so the trail of "what the user reported → what we did" is auditable. (Plan Part 1 §11, Part 7, Part 6 ledger discipline.)
- [ ] **FEEDBACK-02**: In its default (full) mode, `/bgsd-feedback` re-runs the entire two-loop machine on the feedback items — it routes each item through the v1/v2 classify→route seam, fans the items into worktree(s) off `rehearsal/<run-id>`, runs Loop 1 per worktree, re-merges, and re-runs Loop 2 over the updated `rehearsal/<run-id>` — reusing the existing Loop 1 + Loop 2 controllers unchanged (no rewrite), then returns to the User Review Gate. The feedback items are the new work set; everything downstream is the same machine. (Plan Part 1 §11, Part 5, Part 8 v3, reuses v1 Loop 1 + v3 Loop 2.)
- [ ] **FEEDBACK-03**: With `--fast`, `/bgsd-feedback` SKIPS the loops: the Conductor spawns parallel fix agents (or a single agent for a single trivial fix — it decides, from item count/complexity) off the feedback items with NO computer-use verification, applies the fixes to `rehearsal/<run-id>`, and returns to the User Review Gate — handling both the multi-fix and single-fix cases; only the loop (and its verification) is skipped, per Part 1 §11. `--fast` fixes route to Haiku/Sonnet low effort per the Part 11 "`--fast` fixes (no loop)" row. Because `--fast` deliberately has no Tester pass, it is clearly marked as the un-verified path and still returns to the human gate (no silent green — NFR-06). (Plan Part 1 §11, Part 7, Part 11 `--fast` row.)
- [ ] **FEEDBACK-04**: Feedback mode is bounded and routed like every other autonomy path — full-mode re-runs respect `max_iterations` and the per-run budget cap (NFR-08), the decision of multi-agent vs single-agent vs full-loop vs `--fast` is a deterministic scored choice (item count/complexity, NFR-05), and the feedback round is recorded into the run ledger + CHANGELOG so the next PR body reflects the feedback iterations. Feedback never writes `next`; it lands on `rehearsal/<run-id>` and worktree branches only (NFR-01). (Plan Part 1 §11, Part 6, Part 11, NFR-01/08.)

### Per-Agent CHANGELOG Into the PR (CHANGELOG)

- [ ] **CHANGELOG-01**: The Conductor aggregates each agent's changes (across Loop 1, Loop 2, and any feedback rounds) into a single human-readable, **per-agent** CHANGELOG — what each subagent added/fixed/changed, traceable to its commits/branch — by reusing and enriching the v2 CHANGELOG seed (`generateChangelog()` from `rehearsal.mjs`, which v2 built into the run ledger but did NOT wire into a PR). Aggregation/assembly is deterministic file I/O (NFR-05); any prose enrichment is the Part 11 "doc aggregation / CHANGELOG generation = Haiku/low" call, fed only the per-agent summaries. (Plan Part 6, Part 1 §10, Part 11 docs row, reuses v2 REHEARSE-04 seed.)
- [ ] **CHANGELOG-02**: The aggregated CHANGELOG is assembled into a complete **PR description** (title from the run id/slug + prompt, body = the per-agent CHANGELOG + the integration result + a link to the run ledger), produced as a pure, deterministic string-building step so the exact PR body is unit-testable without touching git or GitHub. The same body is surfaced to the human at the User Review Gate (terminal AND would-be PR description, per Part 1 §10) before any PR is opened. (Plan Part 1 §10, Part 6, Part 7, NFR-05.)
- [ ] **CHANGELOG-03 (HUMAN-GATED real PR creation)**: Wiring the CHANGELOG into an ACTUAL PR — running `gh pr create` (or equivalent) with the assembled title/body — is built + unit-tested in isolation behind a mocked git+gh boundary first (CHANGELOG-02), then exercised only via an explicit, off-by-default `--live` opt-in (`changelog-pr-live.mjs` with the `requireLiveFlag()` guard), and the PR ALWAYS targets a NON-default branch (never `next`); the guard hook rejects any PR against the default branch (NFR-01). A `--dry-run` default prints the would-be PR (title + body + base branch + head branch) and exits without creating anything. The real PR is created manually by the human, never in CI. (Plan Part 1 §9–10, Part 8 v3 "per-agent CHANGELOG into the PR", NFR-01/10; mirrors the `*-live.mjs` guard pattern.)

### Docs (DOCS)

- [ ] **DOCS-07**: A `/bgsd-user-eval` + User Review Gate + Loop 2 page (GSD-Mintlify style, diagram-first) documents the integration half of the run end-to-end — assemble `rehearsal/<run-id>` → Loop 2 (boot integrated app → Integration Tester → parallel fix agents → re-merge → re-verify) → User Review Gate (boot servers, localhost URL, checklist, selector verdict) — with the two-loop diagram (Loop 1 vs Loop 2 symmetry) and the exact human-gated `--live` steps for the live integration run (and the `--dry-run` default). (Plan Part 14, Part 5, Part 7, mirrors v0/v1/v2 docs cadence.)
- [ ] **DOCS-08**: A `/bgsd-feedback` + CHANGELOG-into-PR page documents feedback mode (full re-run-both-loops vs `--fast` parallel-fix-no-loop, when each is chosen, the un-verified caveat of `--fast`), the per-agent CHANGELOG → PR-description flow, and the exact human-gated `--live` steps to open a real PR against a non-default branch (and the never-touch-`next` rule), so a user can drive feedback + PR creation from the docs alone. (Plan Part 14, Part 7, Part 1 §10–11, Part 6.)
